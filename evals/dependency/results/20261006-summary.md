# Dependency backtest 20261006 (the author's memory home)

Does a `fact.updated` event predict a change to the notes that declared a dependency on that note?
Run with `python3 evals/dependency/backtest.py`. No model calls; the history is the dataset.

- 426 commits carrying a resolvable `fact.updated` event, over 22.9 days
- 923 (commit, note) events in them; 313 were on notes nothing links at all, leaving 610
- 2034 candidate (event, declared dependent) pairs

| bucket | pairs | share | meaning |
|---|---|---|---|
| same | 21 | 1% | the author updated the dependent in the same commit |
| later | 372 | 18% | the dependent caught up in a later commit |
| never | 1641 | 81% | never touched about it: did not need it, or stale for good |

Catching up later took a median of 1.7 days (max 15.7, n=372).

## The controlled comparison (2-day window)

| | hits | windows | rate |
|---|---|---|---|
| after a real `fact.updated` event | 195 | 1726 | **11.3%** |
| after a random placebo time | 176 | 5178 | 3.4% |

**Lift attributable to the event: +7.9%, about 3.3x chance.**

## What it means

The dependency effect is real and it is far too diffuse to notify on. An event whose note has any
dependents has 3.3 of them, of which 0.38 are actually touched within two days, so a
mechanism firing per pair would be right about one time in nine. That is consistent with the
2026-09-28 hand-judged study, which found 62 real dependents among 263 candidates (24%) — judging
"should have changed" where this counts "did change", so this sits lower, as expected.

**11.3% is the bar.** Any future dependency mechanism has to beat it as a selector on this
same backtest, which re-runs in minutes for nothing. Until something does, the answer is not to build
one: see the review queue removed in 0.4.0, and `decision-dependency-notification` in the author's memory.

## Two invalid controls, kept as a warning

1. **Window after each event vs the window before it.** The log ends at HEAD, so recent events have
   no room for an "after" window while "before" is always full. Reported a large negative lift.
2. **The same, restricted to events where both windows fit.** Still wrong, and the interesting way:
   every pair had a prior change, 2034 of 2034, because *acquiring the link is itself a change to the
   dependent's text about the note*. The before-window was measuring link creation.

Only the placebo design answers the question: same pairs, same window length, start time moved to
somewhere no event occurred.
